## 2. やったこと

### 2-1. バックエンドを新規に作った

固定データではなく、**実データで動く**ものを作った。

| 段階 | 内容 |
| --- | --- |
| 標高取得 | 国土地理院 DEM5A（5mメッシュ）タイルを対象地域ぶんモザイク化。488×443、1セル3.88m |
| 地形解析 | 窪地の深さ・流域面積・傾斜・近傍との高低差を算出 |
| 危険度推定 | 上記を合成して0〜1の危険度ラスタにし、危険地点171件を抽出 |
| ネットワーク | OSMの歩ける道でグラフを構築（ノード10,765／辺13,332） |
| ルート探索 | ダイクストラ法を、コスト関数だけ替えて2回まわす |
| API | FastAPI。4エンドポイント |

**地形解析の中身**

- **窪地の深さ** — priority-flood 法で窪地を埋め、埋める前との差を取る。
  これがそこに溜まりうる水深にあたる。
- **流域面積** — D8 の最急降下方向をたどり、どれだけの範囲の雨水が
  そのセルへ集まるかを積み上げる。
- **傾斜** — 標高の勾配から求める。水がはけるかどうか。
- **近傍平均との高低差** — 半径およそ30mの平均標高との差。

**ルート探索**

```
最短ルート : コスト = 距離
回避ルート : コスト = 距離 × (1 + 4.0 × 実効危険度)
```

危険な区間を「実際より長い道」として扱うことで、遠回りしてでも
避ける経路が選ばれる。実効危険度は、辺の危険度に雨量の倍率
（弱雨0.55／中雨1.00／強雨1.45）を掛けたもの。

### 2-2. フロントをAPIに接続した

- `src/api/client.ts` を追加。バックエンドへの入り口はここ1つだけ。
- `mockRouting.ts` を削除し、表示用の関数だけ `src/data/places.ts` に残した。
- レスポンスの型を `src/types.ts` の `SearchResult` に合わせたので、
  フロント側に変換コードは1行も要らなかった。
- 雨量を切り替えると検索が走り直すため、直前のリクエストを
  `AbortController` で中断し、さらに通し番号でも古い応答を弾いている。
- Viteのプロキシで `/api` を `localhost:8000` に転送。開発中は同一オリジンになる。

### 2-3. 動作を止めていた不具合を直した

いずれも見た目ではなく挙動の問題。

1. **地図のcanvasがコンテナに追従しない** — 初期化時の400×300のまま固定されていた。
   `ResizeObserver` で `map.resize()` を呼ぶようにした。
2. **危険地点をクリックすると検索結果が消える** — MapLibreはレイヤー個別の
   ハンドラとは別に地図全体のハンドラも呼ぶため、出発地の選び直しとして
   扱われていた。危険地点の上なら無視する。
3. **ルート線が描かれないことがある** — `isStyleLoaded()` が true でも、
   load ハンドラでのソース追加はまだ済んでいない場合がある。
   レイヤーの準備完了を state で持ち、揃ってから描くようにした。
4. **ポップアップが古い雨量の文言のまま残る** — 雨量を変えたときに、
   同じ地点の新しい判定内容へ差し替えるようにした。

### 2-4. アプリの質を上げた

- **地点名を出すようにした** — 「地点 (35.6814, 139.7608)」では、
  デモを見ている人に何も伝わらない。OSMから駅・施設・名前つきビルを865件集め、
  「東京駅」「アーティゾン美術館 付近」「丸の内仲通り 付近」と言い換える。
- **デモ対象地域を地図に示した** — 外側を薄く覆う。範囲外をクリックして
  エラーで気づく、という手戻りが無くなる。
- **迂回しても改善しない区間は、そう言い切る** — 危険度が3ポイント以上
  下がらないときは回避ルートを勧めない。
- **バックエンドの生死を先に確認する** — 画面を開いた時点で `/api/health` を
  叩き、落ちていれば検索ボタンを押す前に知らせる。
- **道から遠すぎる地点を弾く** — いちばん近い道まで120mを超えるなら400を返す。
  無理に寄せると、ピンとルートの始点が大きく離れて見える。
- **最近傍ノード探索を格子索引に変えた** — 全ノードの線形走査では、
  対象地域を広げたときに効かなくなる。
- **縦並び（720px以下）の余白を詰めた** — 「ルートを検索」まで
  スクロールしないと押せない状態だった。

## 3. 技術的な判断と、その理由

**危険度モデルを一度組み直した。**
最初は「窪地・流域・傾斜・高低差」の重み付き和で作った。だが都心部は
全体が平坦なため、全区間が0.2前後に潰れ、回避ルートを選ぶ意味が
数値に出なかった（実測：歩道上の危険度の5〜95パーセンタイルが0.13〜0.38）。
原因は、傾斜の項が全区間に同じ下駄を履かせていたこと。
そこで **危険度 =（水が集まる度合い）×（水がはけない度合い）** の形に変え、
傾斜を加算項から倍率に移した。流域面積も、絶対値ではなく
対象地域の歩道上での分布で正規化した。結果、中央値0.02／最大0.99まで広がり、
道ごとの差が出るようになった。

**危険度（%）を「遭遇確率」として定義した。**
地形スコアの平均にすると、「ほとんど安全だが一箇所だけ深刻」なルートが
薄まってしまう。区間ごとの遭遇率を距離で積み上げ、1回も出くわさない
確率の余事象を取る形にした。同じ危険度の道でも長く歩けばそれだけ
出くわしやすい、という直感とも合う。

**生成済みデータをリポジトリに含めた。**
4.5MBのバイナリが入るが、クローンした人がすぐAPIを起動でき、
デモ当日に国土地理院やOverpassへの通信が要らない。
ハッカソンでは後者の価値が勝つと判断した。

**リクエスト中に外部APIを叩かない設計にした。**
重い地形計算は `scripts/build_data.py` で事前に済ませ、起動時に一度だけ
読み込む。リクエストごとに行うのはダイクストラだけ。応答は約25ms。

**地点名は、駅を優先するようにした。**
半径で正規化した距離だけで選ぶと、有楽町駅の27m手前で
「角川シネマ有楽町 付近」（11m）が勝ってしまう。駅が150m以内にあるときは
駅を優先する。駅のそばなら、人はその駅名で場所を言うため。

## 5. 確認したこと

- 出発地・目的地の選択 → 検索 → 2ルートと危険地点の描画
- 弱雨・中雨・強雨の切り替えで危険度が上がること
- 危険地点クリックで判定理由が出ること、そのとき検索結果が消えないこと
- 対象地域外・同一地点・道から遠い地点・不正な雨量、それぞれのエラー表示
- バックエンドを落とした状態での表示
- スマートフォン幅でのレイアウト

## 6. 割り切った点

発表の「今後の展望」に回すもの。

- 危険度は**地形だけ**からの推定。排水設備・舗装材・実際の冠水履歴は見ていない。
  絶対値ではなく、同じ地域の道どうしの相対比較として読むのが正しい。
- 標高はDEM5A（地表面）なので、高架下・地下道など立体交差の扱いは正確ではない。
- 対象地域はデモ用に絞っている。範囲外の指定は400で弾く。
- 雨量は弱・中・強の3段階固定。実況雨量（アメダス等）とは連携していない。
- 東京都のオープンデータ（浸水実績図など）との突き合わせは未実施。
- 利用者投稿による補正は未実装。
